## 一、结论先行

**推荐方案 2：以 `git` 为游戏宿主，把 `pro` 的 3D 渲染与交互能力改造成可嵌入的表现层，放入现有 `main-viewport`，仅在 `GameMode === 0` 的门派场景中启用。**

不是把两个 `index.html` 拼接起来，也不是把 `pro/viewer.js` 原样引入。准确分工是：

- **`git` 负责“游戏发生什么”**：模式、地点、NPC 所在地、行动、剧情、LLM、提示词、变量、存档、事件、Gal 及现有 UI。
- **3D 层负责“如何显示和点击”**：模型、相机、光照、季节表现、地点拾取、NPC 站位及动画，把点击意图交回游戏。
- **只保留一套游戏状态、一套 LLM 流水线、一套存档体系、一套 Android 应用身份。**

两种方向技术上都能实现，但当前目标是“现有完整游戏的养成场景 3D 化”，不是“以 3D 引擎为中心重做整款游戏”。方案 2 的改动边界更小，能逐步上线、保留旧存档，并随时回退到 2D。方案 1 会将 Gal/UI/全局变量/存档/原生插件一起纳入迁移风险，并不会免除 3D 与游戏状态适配工作。

### 最重要的五个事实

1. `git` 不是只有一个简单文字界面，而是已具备复杂业务和持久化链路的游戏宿主。
2. `pro` 已有真实主场景、12 个子场景和导航生命周期，值得复用；但其入口仍是全页预览应用，不是现成组件。
3. 两边的“刷新 NPC”语义不同：游戏按既有规则分配角色；预览器随机分配三名演示角色。两套逻辑不能同时掌权。
4. `main-viewport` 不是空画布：Gal 图层、属性/关系页、事件、交互弹窗和部分子游戏都使用它，不能整体替换。
5. 网页与 APK 都有可行的技术路径，但“现有预览 APK 可打包”不等于“整合后的游戏已通过真机兼容测试”。

## 四、两种合并方向的对比

这里明确命名，避免“A/B”歧义：

- **方案 1：游戏进 3D 项目** —— `git → pro`，`pro` 作为主项目。
- **方案 2：3D 进游戏项目** —— `pro → git`，`git` 作为主项目。

| 维度 | 方案 1：以 pro 为基础 | 方案 2：以 git 为基础 |
| --- | --- | --- |
| 技术可行性 | 可行，但接近整款游戏的宿主迁移 | 可行，边界是场景表现替换 |
| Gal、提示词、变量、LLM | 全部进入迁移/回归范围 | 主体保留，只新增状态通知边界 |
| DOM/UI | 需重建或完整搬入大量现有页面结构 | 保留现有结构，限定修改背景/场景表现区域 |
| 3D 场景复用 | 保留 3D 壳，但仍要改 NPC、导航和业务接口 | 保留 3D 核心，剥离/适配预览外壳 |
| 游戏状态一致性 | 容易形成预览 state + 游戏 state 双中心 | 游戏为唯一事实来源，3D 为只读投影 |
| APK | 需迁移身份、SDK/插件与构建基线 | 继续使用现有游戏 APK 工程，新增资源阶段 |
| 旧存档风险 | 换 origin/appId/存储初始化时风险高 | 保持原 identity 和存储协议，风险较低但仍需测试 |
| 分期交付 | 半迁移期间难保证整款游戏可用 | 可按“主场景→单子场景→全部地点”迭代 |
| 回滚 | 需要维护完整旧游戏分支/版本 | 关闭 3D 开关即可继续 2D 游戏 |
| 对当前需求的成本 | 高；大量迁移并不产生新增玩法价值 | 中；工作集中在组件化、桥接和端侧验证 |
| 长期维护 | 若真要彻底重构，可另立项目论证 | 可渐进整理，无需以一次重写为前提 |

### 为什么不因为 pro 使用 Vite 就选择方案 1？

**构建工具与游戏宿主是两个独立决定。** 完全可以保留 `git` 的网页和业务脚本，只为 3D 子模块增加 Vite 构建。打包输出仍然是静态 HTML/JS/CSS/GLB/WASM，不需要在部署服务器或 APK 中运行 Node/Vite。

反过来，把完整 `git` 原封不动复制到 `pro`，再让它成为真正入口，也许能少改一些业务，但架构本质已经变成“现有游戏宿主 + 3D 模块”，即方案 2；只是换了目录名字。

### 什么情况下方案 1 才值得重新考虑？

若后续目标改成“整个游戏（含 Gal）围绕 3D 世界重做 UI/路由，愿意重构全局状态并接受长周期回归”，可重新立项评估。但这不属于本次“只改养成场景、保留其他功能”的目标。

### 5.1 main-viewport 的所有权

建议增加稳定的专用 3D 容器，例如 `#sect-3d-root`；这是设计建议，不是已存在接口。

- 保留 `map-scene`、各 `xxx-scene` 的逻辑 active 状态以及地点操作控件。
- 3D 开启时，只针对门派地图/地点隐藏旧背景和重复立绘/热区，不移除承载业务的 DOM。
- 原因：自由行动、NPC 互动、pipeline 等仍会读取 `.scene.active` 推导地点。若直接删掉所有旧 scene，只剩 canvas，提示词地点和行动逻辑也会出错。
- 明确层级：3D 背景/场景 → 地点操作 UI → NPC/地点弹窗 → 事件/系统模态层。透明布局区域不要无条件吞掉 canvas 事件；按钮区域也不能点击穿透。
- 不能让 pro 的全局 `.ui`、`.toolbar`、`button`、`body[data-scene]` 规则污染 Gal 和系统界面。
- 属性/关系页即使仍是 `GameMode=0`，也不是应显示 3D 的门派场景。启用条件必须同时包含模式、当前可见 scene 和覆盖层状态。

### 5.2 桥接契约摘要

以下为阅读摘要，精确返回值/错误/重试语义以13.3、13.9为准。规范组件方法：

| 方法 | 职责 |
| --- | --- |
| `mount(container, options)` | 创建一个实例；显式 `assetBase`、画质、事件回调；无全局自动初始化 |
| `applyState(viewModel)` | 显示已确认的地点、NPC、季节、昼夜；不得反向写 gameData |
| `setVisible(value)` / `setRenderEnabled(value)` / `setInteractionEnabled(value)` | 分别控制层可见、持续绘制和输入；静帧弹窗与真正隐藏分开 |
| `retry()` | 最新快照原地重试，不伪造业务revision |
| `resize()` | 依据容器尺寸更新 camera、renderer、后期 target、标签 |
| `destroy()` | 取消请求/动画/事件，释放图形资源；重复调用安全 |

建议 ViewModel 仅包含：协议版本、状态 revision、模式、可见逻辑场景、游戏地点 ID、NPC 的 ID/地点/可见性/显示资源、季节、时间，以及必要的显示/输入标志。

**不要把 API key、完整提示词、对话历史、向量库或整个可变 `gameData` 交给 3D。** 3D 不需要它们。

建议事件仅表达意图：`locationIntent`、`npcIntent`、`returnIntent`、`ready`、`error`。不要让 3D 自己执行扣行动点、推进周数、保存或调用 LLM。

桥接收到意图时重新校验合法地点、角色存在且在场、当前模式，以及宿主既有的生成/模态输入锁。不能只看是否正在流式输出，因为召回准备阶段也可能已经锁输入；不能借 3D 点击绕过原界面的禁用状态。相机旋转/缩放/归位不发 LLM 请求，也不消耗行动点。

### 5.3 状态更新不能只绑一个函数

至少覆盖以下路径：

1. 初始化、开局、载入存档和导入后恢复。
2. `goToLocation` / `switchScene`。
3. `backToMap`：`index.html:2529–2536` 直接改 DOM 和 `userLocation`，绕过 `switchScene`。
4. `returnFromSLG` 与特殊事件写入 `GameMode`：例如 `special-event.js:4274`。
5. LLM 提交 SIDE_NOTE 后，包括模式、地点、NPC、昼夜变化。
6. 周推进、NPC 刷新和 NPC 可见性更改。
7. 重生成的 `restoreFromSnapshot`、切档、正文展开/收起和 UI scene 切换。

`index.html:5928–5938` 已包装一次 `window.switchScene` 处理旧地图热区。新增适配时不要继续堆叠多个相互不知情的包装器。建议在少量明确的提交/渲染边界调用一个幂等协调函数，并批量合并更新；不在每帧轮询所有游戏变量，也不让 MutationObserver 反过来成为游戏规则来源。

恢复时还要处理一个既有边界：`restoreFromSnapshot` 主要恢复数据，不统一重建路由；部分重生成路径按当前旧 active scene 刷 NPC。必须明确恢复完成后的 `logicalPage` 与 `userLocation` 如何协调，不能让 3D 跟恢复后的地点、旧业务 DOM 却停在另一地点，也不能因 LLM 改地点而把正在看的属性/关系页强行关掉。

同时，用户中断生成、API失败、提交异常快照恢复是不同路径；不要为了简化 3D 状态同步，把所有错误一概解释成“撤销本轮全部业务”。

### 5.4 导航一致性与异步竞争

建议优先保持游戏原有“前往地点立即生效”的语义：

1. 点击 3D 建筑，转换为游戏地点 ID。
2. 若需要保留现有体验，先展示地点/NPC 信息，再由“前往”触发；是否改成一步进入须作为 UI 决策单独确认。
3. 宿主调用既有地点操作，提交逻辑地点与 active scene。
4. 3D 跟随渲染；加载失败则在**同一个逻辑地点**展示原 2D 界面并提供重试。

不能直接照搬 pro 的“失败回到主场景”而让游戏已经处在子地点；更不能为了视觉回退把行动、周数或已提交 LLM 结果一起撤销。

每次异步加载携带 revision/generation。读档、切 Gal、换地点、销毁时，废弃旧任务；旧任务晚到不能重新显示过期场景、重新启用控制器或抢走输入焦点。取消加载与“返回游戏地图”是两个不同操作，按钮含义必须清楚。

特别注意：`pro/viewer-interiors.js:178–179` 当前只接受主场景→子场景；游戏的 LLM 更新和读档却可能直接从地点 A 跳到地点 B（见 `git/module/game-events.js:383–415`）。适配器必须实现幂等的任意目标场景同步，不能只调用 `enterInterior(B)` 后忽略其返回 false。内部可先退场再进场，但中间过程不能反向把游戏地点写成地图。

`AbortController` 可以取消 fetch，但不能保证正在进行的模型解析/编译瞬时终止。除了取消请求，还必须有“结果过期则不应用并释放”的保护。

### 6.3 NPC 刷新必须分成两层

**业务分配层继续使用游戏规则：**

- `index.html:2390–2495` 保留玩家当前地点的人物。
- 其余人物按现有位置概率重新分配，检查可见性、`none`，通常每地点分配上限 2。
- `game-helpers.js:494–508` 在人数超过 3 时随机显示 3，是显示策略，不是数据库永远最多 3 人的保证。
- 特殊事件、LLM、读档仍可能带来不同人数，应测试拥挤而非假定只会两人。

**3D布置层只负责：**给原displayNpcs在本地点已经选中显示的最多3人选floor站位、方向、大小和动画，完整在场集合仍保留。不得调用drawAssignments再决定角色去哪，也不得为了取名单再调displayNpcs；异常旧档按13.9B处理。

建议首版隐藏 pro 的“随机刷新全山三人”调试按钮；如保留玩家刷新入口，调用现有游戏刷新函数，刷新后再投影。重试图片/重新计算站位不能改变游戏 NPC 所在地。

位置布局用确定性 seed（例如存档会话标识 + NPC 分配修订 + 地点 ID），保证普通 UI 刷新不会人物到处跳。站位失败时使用保守预设点位或 2D 列表，不能把业务角色删掉。

点击人物要输出游戏 NPC ID，复用 `showNpcInfo` / 互动 / 送礼 / 切磋业务。原地点弹窗依赖 `currentTarget.getBoundingClientRect()`；NPC 古风框选还会查找 `${location}-npcs` 内的 `.npc-portrait` 并复制立绘样式（`game-helpers.js:712` 起）。隐藏旧立绘后直接传假事件并不足够。需明确新增屏幕锚点/人物框接口，分别适配两套主题，保留菜单内容和业务规则而不是强行复用旧定位实现。

### 6.4 时间和环境

游戏已有 `seasonStatus`、`dayNightStatus` 和剧情时间变量。3D 的自动昼夜目前是预览效果，不应自行推动游戏时间。

`currentGameTime` 在 `game-events.js:353–376` 随回复更新，但 `game-state.js:256–305` 并未把它作为显式字段同步保存。因此不能假设旧档能恢复精确时分；本次不要为了接光照擅自修改存档时间语义。

建议优先用有效且属于当前会话状态的游戏时间驱动画面；切档/恢复后没有可信时分时按 day/night 采用明确默认时刻，不能沿用上一存档残留时间。手动调光要么仅为不写存档的画质预览，要么在正式界面隐藏。不要让玩家看到游戏是冬夜而 3D 自己跑到夏日正午。

## 七、嵌入形式：模块化为目标，iframe 仅作可选验证

### 推荐：容器化模块，局部独立构建

- 在 `git` 内建立独立 3D 源码/构建目录与依赖锁，提取 pro 渲染能力。
- 3D 构建输出带命名空间的 CSS、ESM bundle 和资产清单。
- 游戏保留普通 script，通过薄桥接层在需要时动态加载 3D；无需同时迁移全游戏到 Vite。
- `pro` 可继续作为建模/预览工作台，但运行时源码必须规定唯一维护源。建议正式运行模块以 `git` 为准，模型由 pro 按版本化资产包导出；不要长期两边手工维护两份不同的 viewer。
- 新目录名称可以在实施时确定；例如源码 `scene3d/`、发布目录 `assets/sect3d/`，不是本次已经创建的文件。

### iframe 验证路线的利弊

同源 iframe 可以迅速隔离 pro 的 CSS 和全页 DOM，用于验证模型在游戏 viewport 的可读性与手机负载。但它**不是无需改造的最终方案**：

- 地点与 NPC 仍需要桥接，预览器自身随机分配仍需禁用。
- 宿主弹窗、焦点、Esc/返回、输入坐标和暂停仍须跨文档处理。
- 不应把隐藏 iframe 当作已释放图形资源。
- 若使用 `postMessage`，校验来源窗口、精确 origin、协议版本及白名单事件，不传敏感配置，不接受任意函数执行。
- iframe 子页面不持有存档，也不自己调用 Capacitor 插件；这些仍在宿主完成。

**建议直接以容器化为交付目标；只有在容器布局/手机 GPU 风险尚不清楚时，做一次限时 iframe spike。** 不把“先完整做一套 iframe 产品，再完整重做组件”当作默认必经阶段。

## 八、网页部署与 APK 的专项评估

### 8.1 网页部署：可继续纯静态托管

`pro/vite.config.js:15–16` 已采用 `base:'./'`、关闭默认 publicDir，并显式输出资源。该方向适合静态网站及 APK。

但运行时多处用 `location.href` 解析资源，所以仅设置 `base:'./'` 不够：

- 网页可能在 `/char_card_1/` 等子路径，不是域名根目录。
- 游戏页面是根 `index.html`，APK 中又被改名为 `game.html`。
- 3D 资源建议放进专有子目录，必须通过同一个显式 `assetBase` 解析主/子 GLB、NPC 图集、Draco worker/WASM。
- 必须用构建后的 JS，在真实子路径静态托管结构中验证；Vite dev 可用不是交付证明。
- 校验 JS/WASM MIME、大小写、404、CSP 对 worker/blob/WASM 的支持；不要求浏览器运行 npm 的裸模块解析。
- 固定名称的 GLB/NPC 文件要有版本目录或版本查询与缓存策略，避免新 bundle 读到旧模型。

**双击 `file://index.html` 与正常网页部署不是同一要求。** 现有游戏对 file 协议已有特殊资源/CDN处理，但 ESM/fetch/GLB/WASM 不适合承诺在 file 协议下普遍可用。建议 file 模式保留 2D，并提示 3D 请使用本地 HTTP 或线上网页；不要为此要求用户关闭浏览器安全策略。

LLM 的 endpoint/key/CORS 代理继续由原服务负责。静态 3D 资源可离线不代表整个 LLM 游戏离线。现有 Android 环境检测也不能被当成所有服务商 API 都免 CORS 的保证，需要按原 API 路径回归。

### 8.2 APK：沿用 git 原生工程，不合并两套 Android 壳

| 项目 | git | pro |
| --- | --- | --- |
| Capacitor 声明 | 8.4.x | 6.2.x |
| appId | `com.jihaitang.jxz` | `com.jjburst.yunxiu` |
| webDir | `www` | `viewer-dist` |
| 原生插件 | Filesystem、Share | 构建器要求空插件基线 |
| SDK 配置 | min 24 / compile,target 36 | min 22 / compile,target 35 |
| Web 入口 | 开局页→game.html | 3D 预览 index.html |

证据：两边 `package.json`、`capacitor.config.json`、`android/variables.gradle`；`git/apk/build.js:25–36,114–120`；`pro/tools/build-apk.mjs:55–87`。

推荐构建链：

```text
锁定依赖与模型版本
  → 构建独立 3D Web 模块
  → 按清单发布到游戏静态资源目录
  → git/apk/build.js 暂存完整游戏（保留入口重命名）
  → 现有 Capacitor 8 插件同步与 Android 工程
  → Gradle 构建
  → 校验 APK 内实际网页/3D/插件资源
```

注意：

1. `git/apk/build.js:14–23` 是目录白名单；放入已有 `assets` 下可利用复制逻辑，但仍要确保先生成正确产物。放新根目录则必须显式加入清单，不能以为会自动复制。
2. 保留游戏 appId、原签名及 `https://localhost` 的 scheme/hostname 配置；发布升级还须保持签名一致并按规范提升版本。仅保持 appId 并不足以保证能覆盖安装。
3. `storage-service.js:1213–1244` 的导出依赖 Filesystem/Share 或降级复制。迁用 pro 的空插件构建壳会损失该能力。
4. pro 构建器有环境专用的“绕过 cap sync/copy、临时 staging”设计，并拒绝新增原生插件，不能直接拷贝作游戏打包器。
5. 可借鉴 pro 的 manifest/SHA-256 校验思想，但其校验器硬编码 12 景、三人 NPC、空插件和预览入口，不能原样用于最终游戏包。
6. 游戏当前 Android Manifest 为 `sensorPortrait`，要按竖屏游戏 viewport 测试 3D，不要为了模型好看顺手改变屏幕方向。
7. 两边现有入口都产 debug 包；pro 还明确拒绝 release。若目标是正式发布，签名 release/AAB 与分发平台要求应另设发布验收，不能把 debug 成功说成已经可上架。

### 8.3 资源体积与性能

按已校验的 pro 部署清单统计（字节，不是估测）：

| 内容 | 当前大小 |
| --- | ---: |
| 清单资源加清单文件 | 109,098,389 bytes，约 104.0 MiB |
| 13 个 GLB 合计 | 93,361,204 bytes，约 89.0 MiB |
| NPC 图集及 manifest | 3,253,784 bytes，约 3.1 MiB |
| 参考原画 `1.png` | 10,110,022 bytes，约 9.6 MiB |
| 当前 pro debug APK | 40,834,266 bytes，约 38.9 MiB |
| 当前 git debug APK | 617,217,973 bytes，约 588.6 MiB |

APK 是压缩后的整体产物，**不能把以上 APK 体积简单相加当作最终大小**。GPU 解码后的内存也不等于 GLB 下载大小。首次进入不能全量预载 12 景。

建议：

- 仅 `GameMode=0` 且真正显示门派场景时加载 3D；直接进入 Gal 不下载模型/创建 WebGL 上下文。
- 保留主场景 + 一个子场景的有界缓存思路；移动端评估离开 3D 后延迟卸载。
- 正式游戏不带参考原画、建模源 `.blend`、历史模型、预览截图和开发工具；移除原画需同时移除 viewer 引用和相应清单依赖。
- `fields.glb` 当前约 16.79 MB，是明显的子场景带宽/解析压力点。先记录三角形、drawcall、纹理和峰值内存，再决定合批/减面/压缩，而不是单凭 APK 大小判断流畅度。
- 主模型使用 Draco，但当前子场景 `parseAsync` 没配置 Draco 解码器（`viewer-interiors.js:95`）。若后续给子场景也加压缩，必须同步改 loader，不能只替换 GLB。
- 当前默认 `cinematic` 包含后期；low 主要降 DPR/关阴影，不等于无 bloom/DOF/体积效果。后期 compact 在初始化时决定，运行时 `setQuality` 未完整重建后期质量。因此要设计真正的移动低配档，而非只保留一个下拉框。
- WebGL2 不可用、上下文丢失、WASM/模型失败时回退 2D，并保留所有游戏操作。

#### B. 业务一致性比较方法

- 在**独立测试 origin、浏览器 profile 或可恢复的测试数据环境**运行，禁止覆盖用户真实存档。用同一份 P0 脱敏存档分别初始化 2D 与 3D，用固定业务随机种子/时钟和相同操作序列比较。
- 常规回归使用固定 LLM 响应 fixture，测试层拦截 API/召回等外部请求，不消耗真实 token；保留少量经配置授权的真实 API smoke 给 P5。失败、流式分片、取消、格式截断分别有 fixture，不用“LLM每次回答不同”解释状态差异。
- 比较内容包括逻辑页、游戏地点、模式、NPC位置/可见性、行动点、金钱/好感、周状态、提示词消息结构与中文关键词、游戏存档有效载荷。忽略项仅限测试预先列明的时间戳/随机ID和独立表现配置，**不得忽略地点/NPC等业务字段**。
- 3D美术站位随机数与游戏业务 RNG 隔离，避免加载模型/布置人物消耗随机序列而改变下一次事件结果。
- 图片对比以相同尺寸/画质/相机/环境为前提；跨 GPU 不要求逐像素完全相等。业务用状态断言验证，视觉用截图及人工检查；内存用资源计数与趋势验证，不仅凭“没有崩溃”。

#### C. 阶段进入/退出规则

- P0→P1→P2→P3→P4→P5→P6顺序推进，最小协议/路由/锁/资源规则在P0冻结，后续只扩实现和入口覆盖。各阶段标题中的人日为原功能估算，完整交付排期以P0重估及15.1为准。后续可提前做风险验证，但不能以此替代前一阶段验收。
- 每个阶段必须同时交付实现/配置（如适用）、测试资产和报告；只有界面截图不算完整交付。
- 本阶段必测项与已完成阶段的关键 smoke 全部通过，才可签字进入下一阶段。严重的状态错位、存档损坏、核心交互不可达、模式泄漏或 APK无法启动一律阻断；外观轻微差异需记录并明确接受人。
- 既有缺陷需在 P0 记录；如阻碍新旧一致性验收，应单独约定修复后的行为预期，不能默默改基线让测试变绿。
- P1/P2 仅接当前范围内所需的初始化/模式/读档通知；P4 补齐所有入口，不要求 P1 先完成整个 P4。P1 的 APK smoke 可使用可复现的临时测试暂存流程，P5 才收敛正式一键构建链路。

| P4-T03 回滚与失败 | 固定正常/分片流式响应，分别测试重生成、提交异常触发快照恢复、用户中断、API错误、SIDE_NOTE/摘要截断；让3D请求晚到 | 按原路径分别判断是否提交/恢复/自动存档，不把abort当rollback；状态恢复后旧DOM与3D无地点分裂；保留各检查点状态与存档差异 |
| P4-T04 特殊页面 | 两主题下，从养成/Gal进入属性和关系；浏览期间注入地点变化；再返回。另覆盖Gal分页、全文展开、新回复和CG开关 | 属性/关系不会被地点更新强制关闭；返回行为与基准一致；Gal图层和事件选项无3D残影/遮挡 |
| P4-T05 子游戏及UI | 打开农田、炼丹、战斗、21点、世界地图并完成一次可重复结算；操作背包/交易/技能、历史、长弹窗和软键盘 | 输入优先级正确；iframe消息只结算一次；原按钮、BGM和返回路径不退化；覆盖层期间3D输入关闭，按可见性策略停绘 |
| P4-T06 配置/存档隔离 | 修改提示词覆盖、世界书和API测试配置后切档；导出再导入；扫描序列化payload | 全局与随档配置范围不变；无Three/DOM/renderer对象；旧档无3D字段仍可用；报告不得泄露API key |
| P4-T07 原生导出 | 在沿用游戏插件的Android测试包导出脱敏存档，经系统分享接收后重新导入；另模拟插件失败 | 分享导出有效，失败时复制fallback有效；导出内容可恢复，不能只验证“分享面板弹出” |

**退出门槛**：入口表无未覆盖项；固定fixture业务/prompt比对无未解释差异；P0–P3关键smoke通过。受既有恢复错位影响的用例必须有批准后的预期与修复范围，不能跳过后宣称兼容完成。

**统一采样协议**

- 每个设备记录型号、RAM、Android/WebView/GPU、屏幕与容器尺寸、DPR、画质、充电/温度条件。桌面记录浏览器/GPU；模拟器只作补充。
- 热场景先预热30秒，固定相机与交互序列采样60秒，共3轮；保存原始帧间隔或结构化统计及聚合方式。真实pipeline生成按13.9C停绘，单列正文响应/锁释放；如要测渲染与正文并发压力，由测试页注入不带业务锁的合成正文负载，明确非真实操作模式，不能关闭生产锁来测FPS。
- 主场景冷进入、子场景冷进入各至少5轮，冷/热缓存分开：冷测试清测试缓存并新启进程，不清用户数据；说明系统磁盘缓存不可完全控制。测量从操作开始到真正可交互，不仅到HTTP下载完成；报告各轮值、中位数和最大值，样本少时不包装成可信p95。
- 网页慢网记录明确限速/延迟与缓存状态；不与APK本地资源时延混在同一表。
- 内存同时观察renderer资源计数与可取得的进程/JS内存趋势；进程内存不当作纯GPU显存。若浏览器不提供某指标，标记不可获取，不能编造为0。

**退出门槛**：同版网页与APK校验通过；两台Android有真实结果，至少指定中端设备真实3D达到约定指标，低端可明确通过2D fallback；P4核心流程在最终包复测。两台都仅2D不算双端3D目标完成。阈值调整必须说明证据并单独批准，不能测后悄悄降低标准。

## 十、验收矩阵与建议性能目标

### 10.1 必测矩阵

| 类别 | 最少覆盖 |
| --- | --- |
| 模式 | 养成冷启动、Gal 冷启动、0→1→0、属性/关系返回、剧情自动切模式 |
| 场景 | 地图与 11 地点；连续快速点击；加载失败/取消；重复进出；厢房入口关闭 |
| NPC | B/C/I 动画，其余静态；空场、隐藏、none、未知 ID、多于3人、站位失败、刷新与读档 |
| LLM | 固定响应 fixture 的 SIDE_NOTE、模式/地点/时间变化；流式与非流式；取消/失败/重生成 |
| 数据 | 旧档/新档、切档、快照恢复、导入导出、提示词覆盖和 API 配置保留 |
| UI | 正文展开/收起、Gal 分页/CG、事件覆盖、炼丹/农田/战斗/世界地图、两套主题 |
| 网页 | 本地 HTTP、HTTPS 子路径静态部署、窄屏/桌面、file 模式 2D回退 |
| APK | 原签名覆盖升级、断网资源、后台/前台、锁屏恢复、原生分享导出、返回键和软键盘 |
| 故障 | WebGL2 不可用、context lost、GLB/PNG/WASM 404、旧资源缓存、晚到请求 |

### 10.2 建议验收指标（待 P1/P2 真机基线校准）

- 中端 Android 默认低配，在约定复杂场景连续交互，目标中位帧率 ≥30 FPS，p95 帧耗时 ≤50 ms；桌面 balanced 目标 ≥50 FPS。必须注明设备、WebView、viewport、DPR、场景和测量区间，不混用 headless（无头浏览器）数据宣称真机性能。
- 本地 APK 冷进入 3D 主场景暂定 ≤5 秒、子场景 ≤3 秒（中端测试机，按P5协议至少5轮的中位数判定，并公开最大值）；不达标先降质/加明确加载反馈，再决定默认开关。
- 网页冷加载按资源大小与约定网络档记录各轮值及p50；样本量足够时另报p95并注明样本数，不承诺16 MB子场景在慢网也固定几秒打开。
- 连续 30 次主/子场景切换、20 次 3D↔Gal 切换，geometry/texture/renderer 数量与内存趋势须收敛，不持续单调增长。
- 同时只维护一个 3D renderer；隐藏/Gal/长期覆盖时绘制计数不继续增长。后台停止或暂停请求/动画的行为有可检查证据。
- 所有纳入兼容测试、原本能运行 2D游戏但禁用/不支持 WebGL2 的环境，都应通过 2D回退验收，不把图形失败升级成整款游戏不可玩。
- 任何 LLM/存档业务验收优先于画面指标；不能为了保帧而丢 NPC、吞点击或延迟提交业务状态。

## 十一、风险分级与回滚

| 优先级 | 风险 | 应对 |
| --- | --- | --- |
| P0 | 两套状态互相改 NPC/地点 | 宿主唯一权威；3D只发意图与读 ViewModel |
| P0 | 移除旧 scene 导致行动/提示词地点错误 | 保留 DOM 契约，再逐步解耦 |
| P0 | Gal/事件/读档绕过单一监听点 | 明确提交边界，幂等协调与 revision |
| P0 | 替换 Android 工程导致插件/旧数据丢失 | 沿用 git identity、origin、签名、插件和原生壳 |
| P1 | 路径只在 Vite dev 成功 | assetBase + 子路径生产构建 + APK资源校验 |
| P1 | 手机后期过重/内存泄漏 | 真低配档、单实例、有界缓存、完整 destroy、2D降级 |
| P1 | 动态素材只有三人 | 静态卡/人物列表兜底，不把补全美术作为阻塞 |
| P1 | 11/12 地点差异、预览文案不符 | 显式映射、厢房未开放、宿主提供文案 |
| P2 | 历史文档/测试与现状不符 | 以当前源码为准，冻结版本并更新自动化契约 |

回滚分两层：

1. **运行时回滚**：关闭 3D，停止并释放组件，恢复原背景/立绘/热区，业务地点和存档保持不变。
2. **版本回滚**：恢复上一套完整网页/3D产物及清单，避免只回退 JS 不回退模型。APK 必须考虑版本号与签名限制，不能把直接降级安装当作通用方案；最稳妥的紧急处理是发布更高版本、默认关闭 3D。

## 十二、实施前的最终建议

1. **采用方案 2，不迁移 Gal、提示词管理、变量管理和存档核心。**
2. **第一目标是打通一条真实业务路径，而不是先把所有场景都显示出来。** 单场景前往→NPC互动→LLM提交→读档一致，比单纯看到12景更能证明整合成功。
3. **将“显示层接入”和“游戏重构”拆开。** 只做必要的通知接口和生命周期边界；既有状态/存档问题单独跟踪，避免责任边界失控。
4. **网页与 APK 共用同一份 3D静态产物，原生工程沿用 git。** 模型制作流程继续留在 pro，不把 Blender、node_modules、预览工具整体搬进游戏发布包。
5. **长期保留 2D备用模式。** 这是旧设备兼容、图形失败容错和逐步发布的产品能力，不是临时补丁。

最终判断：**“以完整游戏为核心增加 3D场景表现”比“以场景预览器为核心迁入完整游戏”更符合当前两项目的实际结构，也更容易守住网页部署、APK打包和既有玩法不退化这三个目标。**


`portraitUrl`由宿主用原资源规则解析后提供；动态图集的`visualKey`仅允许catalog已有键，通过assetBase解析。静态默认身高1.5m只是表现参数，后续可按美术调整，不写游戏年龄/属性。未知季节/非法时间不直接进shader，记录警告并回退有效游戏季节/默认冬季及昼夜时刻。

```js
// 从构建模块取得的规范入口（待实现）
const view = mount(container, {
  protocol: 1, assetBaseUrl, quality: 'low', onEvent
});
view.applyState(snapshot);        // Promise<ApplyResult>
view.setVisible(false);           // 隐藏层，同步停绘/禁输入并失效在途导航
view.setRenderEnabled(false);     // 保留canvas最后一帧，只暂停rAF/动画，不撤掉当前3D显示
view.setInteractionEnabled(false);
view.resize();
view.retry();                     // 当前最新快照原地重试，Promise<ApplyResult>，不改业务revision
view.destroy();                   // Promise<void>，幂等
// ApplyResult: {status:'applied'|'degraded'|'superseded'|'destroyed', epoch, revision, sceneId}
```

- `mount`同步返回handle并登记唯一实例，初始化/模型加载在首次有效applyState中异步完成；同一容器重复mount必须拒绝，不能创建第二个renderer。
- `applyState`验protocol/白名单/数值，clone需要数据；去重限于同一实例中仍有效的已应用状态/在途任务，旧revision拒绝。显式retry、已失效任务恢复与新实例不被同revision去重拦住，详见13.9E。不可变展示对象通过测试验证，而不是依赖调用者不改引用。
- `setVisible(false)`与`setInteractionEnabled(false)`优先级高于旧apply的完成回调；只有宿主最新调用能重新开启。环境/NPC更新不自动等同于重新切场。
- `destroy`之后旧promise返回destroyed/superseded，不能重新创建DOM；再次使用需新的mount。正常资源失败返回degraded并发error，不抛出未处理rejection使游戏中断；参数/协议错误也由bridge捕获并降级。
- 性能计数只通过只读debug接口导出，默认生产关闭；不把`window.__diorama`和Three实例当正式宿主API。

事件格式：

```js
{ type: 'locationIntent', epoch, revision, locationId: 'cangjingge',
  anchor: { space: 'client-css-px', left, top, width, height } }
{ type: 'npcIntent', epoch, revision, gameNpcId: 'F', anchor }
{ type: 'returnIntent', epoch, revision } // 仅普通模式子景的返回地图
{ type: 'ready', epoch, revision, sceneId }
{ type: 'error', epoch, revision, scope: 'scene', code: 'MODEL_HTTP', retryable: true }
```

业务事件必须再次检查epoch、当前模式、合法ID、当前角色在场/被显示、宿主输入锁；拒绝过期事件。`locationIntent`只开信息卡；卡上确认才走原`goToLocation`。view不传任意函数名/HTML/URL供宿主执行。显示标签使用textContent；error文案不直接拼未可信模型字段进innerHTML。

### 13.4 状态协调、路由恢复与竞态算法

**三个版本号不能混用：**

- `sessionEpoch`：会话/数据恢复边界。开始切档/重生成前立即使旧输入失效；恢复成功发布新epoch，恢复失败也不能重新放行旧异步结果，应重新发布当前有效状态。
- `revision`：视图快照差异序号，UI文本无关变化不递增。环境/NPC/可见性变化可递增但不必重载场景。
- `routeGeneration`：渲染器内部切景任务序号，仅目标scene/epoch改变、取消、隐藏时在途导航失效或destroy时递增。**不能每次流式通知或环境变化都abort模型加载。** NPC素材另有独立generation，防止旧卡片晚到。

建议宿主方法：`start()`、`notify(reason)`、`invalidate(reason)`、`reconcileAfterRestore(reason)`、`setPreference(patch)`。`notify`用microtask合并同一同步批次，异步业务事务则在调用方显式begin/end，finally释放；不能用固定setTimeout猜“所有恢复已完成”。`invalidate`同步关闭输入并失效旧任务，不等待下一帧。`reconcile`只读取已完成的业务状态，不调用刷新NPC/LLM/存档。

**路由规范表：**

| 来源/情况 | logicalPage处理 | 业务数据处理 |
| --- | --- | --- |
| 正常前往/返回 | 读取原操作完成后的active scene | 原函数负责userLocation，bridge不再写一次 |
| GameMode=1 | sceneId=null、立即隐藏停绘，保留原Gal底层scene | 不把userLocation强制设为地图 |
| 属性/关系页收到地点变更 | 保持属性/关系logicalPage，sceneId=null | 接受原业务位置更新，不能强制退出属性页 |
| 初始化/读档/成功恢复且不在特殊页 | `userLocation=tianshanpai`规范化为map；有效地点激活相应scene | 仅恢复DOM与当前业务值一致，不改变原业务值、不生成行动 |
| 恢复时特殊页仍可保留 | 保留特殊页；若模式改变，清理过期Gal图层并按现有返回语义更新导航记忆 | 不虚构新存档字段；正常养成返回仍按原行为回地图 |
| 未知地点/无效模式/多个active scene且无法确定 | 关闭3D、显示诊断，保留数据；按已记录的宿主恢复策略显示2D | **不静默改为tianshanpai、不擅自清档** |

`switchScene('map')`本身不写`userLocation='tianshanpai'`，正常返回必须仍走原backToMap。恢复时业务值已经为tianshanpai，宿主可清旧active并激活map，不能调用会发消息/刷新NPC的返回门派事务。既有恢复错位的最小修复需单列测试：恢复到藏经阁后DOM和3D都在藏经阁；属性页恢复则继续看属性页。

**一次渲染协调的伪流程：**

```text
宿主业务事务完成 → normalize logicalPage（仅批准的恢复DOM修复）
→ snapshot与上次比较 → 业务视图变化才revision++
→ 仅普通notify且同实例有效应用/请求仍存在时去重；retry/resume/新实例强制应用缓存的最新快照
→ 非可见门派页：同步停绘/禁输入，取消在途导航，启动30秒卸载定时器
→ 可见门派页：取消卸载定时器；唯一mount（如需）；applyState最新快照
→ 同目标且已有模型：只更新环境/名单/输入，不重新load
→ 新目标：routeGeneration++，abort旧fetch，撤销旧transition
→ 原2D仍为本次逻辑地点；加载/解析/应用语义 → 每个await后检查generation
→ 过期：释放候选资源，返回superseded
→ 当前：NPC/环境绑定、fit相机、compile、首次绘制成功后提交3D可见态
→ 失败：error/degraded，保留本地点2D，允许显式重试
```

不能在旧导航的finally里无条件focus返回按钮或`controls.enabled=true`。焦点只在同epoch、最新任务、无宿主模态且由用户导航触发时恢复；读档/LLM自动移动不抢输入框焦点。场景A→B为一次目标事务，内部退main不发宿主returnIntent。

### 13.5 精确通知清单与输入锁

| 通知来源 | 时机 | 类型/注意事项 |
| --- | --- | --- |
| 初始化最终分支 | 存档/正文/事件选项恢复结束后 | start + restore；不能在DOMContentLoaded或模型ready时猜宿主已好 |
| goToLocation/switchScene/backToMap | 原DOM/地点操作结束后 | navigation；已有switchScene wrapper保留或显式迁到同一通知，不重复包裹 |
| 普通/悬赏下山、returnFromSLG | 模式写入立即invalidate；整个事务结束notify | mode；不等待LLM返回才隐藏3D |
| applyEventEffects | 开始批处理，结束时notify | effects；setValueByPath只标dirty，mode变化立即invalidate |
| parseLLMResponse/_commitResponse | 字段应用期间标dirty，最终展示提交点notify | state；不以普通正文分页元信息驱动导航 |
| refreshNpcLocations/toggleNpcVisibility/displayNpcs | 更新后notify，其中displayNpcs发布实际显示ID列表 | NPC；notify不能反过来再次调用refresh |
| loadSaveSlot/JSON/ST导入/开局loadSave | 开始invalidate，最终UI恢复后reconcileAfterRestore | epoch变化；覆盖所有入口，不仅一个加载函数 |
| 手动重生成/提交catch恢复 | restore成功且相关数据恢复后协调DOM再notify | rollback；API失败/abort不走这条路径 |
| updateStoryDisplay/属性关系页/模态开关/子游戏 | 可见性变化后notify | overlay；不重建业务数据 |

输入锁不能简单等于`inputEnable===0`（它主要控制自由行动等原按钮），也不能简单等于`pipeline.isStreaming()`。默认规则：

1. bridge维护**自身场景输入许可**，不修改宿主`inputEnable`或原按钮disabled。
2. runTurn整个生命周期（准备/召回/请求/提交/异常finally）增加3D专用busy token，开始禁3D游戏意图，结束释放；只保护3D，不改变原pipeline分支的提交或取消语义。
3. 真正可见的宿主模态/stream-mask/子游戏覆盖阻断3D输入；低频观察这些明确节点的class/style变化可以补漏，**观察器仅计算显示锁，不改变游戏状态**。
4. 地点/NPC信息卡打开时冻结相机，卡按钮仍由宿主工作；关闭恢复需确认busy token、epoch和页面仍允许。遮罩/事件选项优先于3D返回按钮。
5. GameMode不为0、非门派页、document.hidden、容器零尺寸、3D加载/错误状态一律不接3D意图。
6. 不默认接管全局R/H/Esc。仅canvas聚焦时可用局部复位快捷键；Esc/Android返回首先遵循现有宿主模态/子游戏行为，首版不为3D新增原生backButton插件。

### 13.6 DOM、弹窗坐标与加载/回退交接

- `#sect-3d-root`作为`main-viewport`内独立子节点，**不使用`.scene`类**。保留所有旧scene、actions、NPC容器、Gal容器与事件节点。
- 加载期间仍显示本次业务地点的2D背景/人物，局部加载提示不吞掉系统菜单；成功绘制后才原子切换到3D背景。CSS启用标记区分`requested`与`ready`，不能仅开关为true就隐藏2D。
- 专用CSS加载一次且全部命名空间化。3D ready时仅隐藏当前门派scene的背景/旧立绘/旧SVG命中面与装饰遮挡；scene透明区域pointer-events:none，操作按钮/卡片pointer-events:auto。不要给整个viewport设pointer-events:none。
- 图层相对关系必须固定：canvas在最底可见层，原scene操作层在其上，人物/地点信息卡更高，stream-mask/事件/系统模态/小游戏保持原优先级。先查现有三份CSS的computed style，再确定数字；不靠无限加z-index覆盖问题，不改Gal全局display规则。
- 销毁/关闭/错误时撤销本组件class和inline属性，恢复被管理的原值；不要用空字符串覆盖用户主题/宿主后来写入的值。避免改动整个body.style或替换className。

**坐标契约**：事件anchor统一为client CSS pixels，不是canvas像素/物理像素；3D世界点投影后用canvas.getBoundingClientRect的left/top/width/height换算。宿主再减viewportRect得到局部坐标，若viewport有CSS transform还需按client尺寸/layout尺寸的比例反变换；DPR只影响drawingBuffer，不乘进弹窗位置。滚动、ResizeObserver和visualViewport resize触发重定位。框限制在viewport/既有弹窗适配区域内；不在屏幕内的人物不能出现屏幕外按钮。

给宿主新增明确的`showNpcInfoAtAnchor(gameNpcId, locationId, anchor)`和`showLocationInfoAtAnchor(locationId, anchor)`入口，原二维入口仍支持原事件。新入口复用数据/按钮动作生成，但不调用依赖隐藏`.npc-portrait`尺寸的旧框选定位代码。名单变化、切场、恢复或进入Gal时关闭旧3D信息卡；卡打开期间暂停相机以稳定锚点。

### 13.7 NPC集合、资源与环境投影细则

1. `displayNpcs`仍按原业务路径执行，发布**它本次实际选出的角色ID序列**。3D读取这个结果，不再调用getRandomLocation/drawAssignments，也不为了得到名单重调displayNpcs。即使3D未开启也保留原行为。
2. 正常数据中`residents`取游戏在场集合、`renderedNpcs`取原displayNpcs已选择子集，none不生成角色。位置/可见性矛盾或未知ID按13.9B处理：关闭该景3D并保留原2D，不在renderer偷偷筛选后制造与人数/prompt不一致，也不修改业务数据。
3. 3D最多为本次选出的3人生成卡片；超员完整人数可显示，但不默认让fallback列表越过原选择集合。缺素材/站位失败的列表只包含本来应显示的角色，保持可互动。
4. `layoutKey`由epoch+sceneId+选中ID序列生成；用独立seeded PRNG计算位置，不用全局Math.random。普通环境/revision更新不重新站位。旧档无需保存世界坐标，恢复时可重新生成同会话合理布局。
5. floor必须是真实mesh，满足`name=floor`与`userData.npcSpawn`；不得简单Box3随便放到家具上。采样达到有限尝试次数即fallback，不同步执行无界重试。
6. texture/cache按visualKey复用，实例独立材质/UV动画状态；共享纹理offset会互相改动画时需独立视图或shader UV。选中高亮不能改所有同材质人物。
7. 当前人物纹理pin住，离景解除pin；默认仅保留当前集合及最近离开的一组，数量上限6个visualKey，超限LRU释放，单个超大图先缩放或列表fallback。保留alpha像素数组需同步释放，不能只dispose材质。
8. 3D调色仅改变表现，不修改npcFavorability等。动态/静态素材名字、尺寸可变但游戏ID恒定；菜单点击发送游戏ID与中文人名，不能传`npc:dongting`进入原提示词逻辑。
9. epoch切换清除时间可信标记。仅在本epoch确认解析到有效HH:MM后使用精确时间；读取到上个会话残留`currentGameTime`不算可信。冻结autoTime与季节调试控件。

### 13.8 生命周期、资源所有权与故障处理表

状态最少包括：`unmounted → idle/loading → ready-main/ready-room → suspended → disposing → unmounted`，另有`degraded`。业务地点不由此状态机定义。

| 资源 | 唯一所有者 | 清理要求 |
| --- | --- | --- |
| renderer/canvas/controls/rAF/ResizeObserver | runtime | 停rAF、remove listeners、controls.dispose、renderer.dispose、移除自有canvas；测试全部计数 |
| 主GLB及环境衍生材质/纹理 | 主场景资源集/environment | 维护Set防重复dispose；退出组件统一释放，不能只释放原GLB而漏shader/天空衍生资源 |
| 子GLB/窗景/floor/候选解析对象 | navigation | 主+单室缓存；新候选已过期也释放；替换时旧房间释放，不保留12室 |
| NPC图集/alpha像素/共享geometry/材质 | NPC资源管理器 | refcount/pin+LRU；解除引用、revoke临时URL、imageBitmap.close如适用；destroy全清 |
| composer/render targets/noise/后期pass | 后期模块 | resize对应target；切换low/balanced先dispose旧管线；不能并行留两套 |
| fetch/Draco workers/延迟卸载timer/过渡动画 | 相应任务或runtime | AbortController+generation；decoder.dispose；清timer/取消WebAnimation；finally不能复活控件 |
| root class/局部加载提示/信息卡 | bridge/UI适配 | 按拥有范围撤销，不清空main-viewport和宿主modal |

安全次序：立即阻断输入与新请求→失效generation→停rAF/动画→取消fetch并解绑控件/观察器→解绑NPC/环境→释放scene与缓存/后期→renderer.dispose→移除自有DOM。不能等所有不可取消的compile完成才停宿主输入；晚到结果仍需清理。

| 错误 | 自动行为 | 用户可做/验收 |
| --- | --- | --- |
| current.json/manifest/entry/CSS缺失或protocol不兼容 | 保持2D，通知明确“3D资源未就绪” | 设置仍能关闭/重试，不影响Gal/存档 |
| 主GLB/renderer/WebGL2失败 | 本次实例销毁，3D降级2D | 显式重试创建新实例；不整页reload |
| 子GLB失败 | 当前逻辑地点使用2D，主实例可保留有界缓存 | 重试同地点/正常返回；不改业务位置 |
| 单NPC素材/站位失败 | 只该角色切名单fallback | 角色信息/互动不丢，不刷新全山NPC |
| context lost | 立即停绘/销毁并2D回退 | 不承诺原上下文恢复；用户可重新启用3D |
| 后期不支持/编译失败 | 当前会话只尝试一次plain low，仍失败则2D | 记录质量降级，不自动无限重试 |
| 旧任务结束/过期点击 | 丢弃并清理 | 无告警刷屏、不抢焦点、不触发业务 |

主加载超时默认30秒、子景沿用60秒、NPC图集20秒；允许配置用于测试。UI始终能返回/关闭3D；timeout按可取消网络处理，不能假装CPU解析必能立刻打断。性能调优不得通过删除NPC、修改提示词或吞业务输入达成。

### 13.9 易错边界的明确补充

#### A. 读取不产生业务副作用

`syncVariablesFromGameData`与`syncGameDataFromVariables`当前都调用Math.random更新randIdx（`game-state.js:252,306`）。**bridge构造快照绝不能调用这两者、displayNpcs、refreshNpcLocations或任何保存函数。** 只在原业务函数既有调用结束后读取变量和已发布的显示名单。额外调用或省略原有调用都会改变后续随机事件，测试必须比较后续一次业务随机结果及RNG调用计数，而不仅是眼前画面。

读取来源固定：模式/地点/季节/可见性来自已完成事务的运行变量；NPC真实位置来自`currentNpcLocations`；逻辑页来自已规范化active scene；已显示子集来自displayNpcs的发布结果；存档恢复先走原同步再取这些运行变量。不得在运行变量与gameData不一致时擅自选择“看起来更完整”的一边。

**Three自身也必须隔离随机源**：当前`three/src/math/MathUtils.js:17–24`的generateUUID每次消耗4次全局Math.random，仅NPC布局私有seed不够。默认采用只作用于3D构建的随机源隔离，不改游戏概率算法：

- 待创建`scene3d/src/render-random.js`私有PRNG，种子用crypto.getRandomValues或明确的表现seed，不从宿主Math.random取种；不用于密钥/签名等安全用途。布局另用按layoutKey固定的seed，不与UUID序列耦合。
- 待创建`scene3d/scripts/isolate-render-rng.mjs`构建transform，在受控3D模块图（包括本包Three依赖）内通过AST/作用域识别，将全局Math.random引用改为导入私有renderRandom的引用；不做字符串盲替换，不修改node_modules源文件，不处理宿主classic业务脚本。helper本身排除以免递归。
- 构建后审计所有在宿主realm执行的3D entry/chunks不残留未隔离的Math.random或动态别名访问；发现不能静态判断的访问则构建失败并审查，不悄悄放过。独立Draco worker的realm不推进宿主随机流，单独登记而非误计业务调用。
- P1生产构建与浏览器测试使用同一transform，不能仅在测试中绕过。开发调试也用该产物，直到dev管线同样通过审计。**不允许在await加载期间临时替换window.Math.random**，会污染同时运行的游戏。
- P0固定全局业务PRNG与计数，P1新增测试：在相同业务轨迹间额外执行Three对象创建/场景加载/销毁，业务RNG计数及后续事件抽样不变；3D私有调用另计。不能只忽略Three计数，因为未隔离时它已推进同一随机流。

这是维持既有随机业务的3D构建兼容层，不是游戏RNG重构。实现前在P0登记该transform/测试工作量并锁定所选AST工具依赖。

#### B. 正常数据与矛盾旧档分开

原`getNpcsAtLocation`只按地点筛选，不验证visibility/未知ID；原刷新也可能保留当前地点的矛盾人物。因此“隐藏仍有地点”“未知Z仍在场”的旧档不一定符合正常显示规则。

默认不在3D工程中修复游戏业务：有效数据应满足已知NPC且可见人物才有可展示位置；若真实名单存在`npcVisibility=false`但仍在当前地点、未知NPC ID等冲突，bridge报告`HOST_ROSTER_INCONSISTENT`并让该场景保持原2D，不改存档、不补人、不改变人数/prompt来源。纯adapter负测验证拒绝/回退，原游戏对异常档的既有问题单列缺陷，不声称本次修好了。若必须支持这些异常档，先批准一个对2D/3D共同生效的清洗规则并更新基线，不能只在3D偷偷过滤后宣称一致。

**“15角色均可访问”指15名角色逐个作为原显示子集成员时都可交互，不要求15人同场全部可点击。** 4/15人拥挤测试检查：原先选中的最多3人不丢、其余仍保留在业务位置和总人数中。完整人物列表若提供额外访问能力，属于另行批准的功能变化。

两主题动作默认保持现状：古风菜单送礼/切磋/互动，扁平菜单切磋/互动（`showNpcInfoPopup:963–971`没有送礼按钮）。“两主题测试送礼”应解释为古风验证送礼、扁平验证不擅自新增按钮；若要求菜单能力统一另作UI决策。

#### C. 菜单自身操作与场景输入分开

锁用原因集合/令牌，不用一个可被任意关闭函数置true的布尔值。至少有：`generation:<id>`、`modal:<id>`、`scene-menu:<id>`、`route:<generation>`、`lifecycle`。

| 状态 | 3D绘制 | canvas拾取/相机 | 宿主菜单动作 |
| --- | --- | --- | --- |
| 正常门派页 | 是 | 是 | 原业务规则 |
| 地点/NPC信息卡 | 可保留静帧（停止rAF） | 否 | 允许该卡自己的前往/互动，仍校验epoch、在场及其他业务锁 |
| stream-mask/生成中 | 停绘 | 否 | 不得绕过生成锁；原中断控件仍可用 |
| 系统模态/子游戏/事件阻挡 | 停绘（保守策略） | 否 | 由原UI处理，不接管返回键 |
| 正文展开但3D仍可见 | 按是否实际遮挡决定，默认保守停绘 | 不让正文点击穿透 | 原分页/收起正常 |
| Gal/属性/关系/后台/零尺寸 | 否 | 否 | 原页面正常 |

信息卡“前往”按钮并不是再次发送canvas意图；它使用卡片保存的epoch/目标，**只忽略自己的scene-menu令牌**，其他generation/modal锁照常检查，成功后关闭该卡再调用原goToLocation。菜单动作触发前重新检查角色仍在场/被显示，不能只在打开时校验。关掉一个模态只释放自己的令牌，两层遮挡关一层仍保持锁。切档/模式改变关闭所有3D自有菜单并失效其回调，不关闭用户其他宿主弹窗。

#### D. 恢复用例的唯一预期

| 场景 | 必须结果 |
| --- | --- |
| 地点A发消息→SIDE_NOTE移B→重生成恢复A | 恢复后的运行地点A、普通逻辑页A、2D/3D都A；重新发送消息仍走原重生成内容，不额外导航/扣点 |
| 在属性页收到LLM移B | gameLocation=B，logicalPage=player-stats，3D隐藏；不得打断属性查看 |
| 从属性页显式载入另一存档B | 跟现有完整读档行为恢复新档的场景/模式及事件，不保留旧档属性页；清旧3D菜单，epoch更新 |
| 属性页内发生同会话快照恢复 | 保留属性页（若原路径保留），仅业务地点恢复；后续返回按原属性页返回规则，不偷换为3D导航 |
| 提交异常恢复 | 恢复成功后按普通/特殊页规则协调；恢复失败则禁3D并显示错误，不编造成功快照 |
| API错误或用户abort | 不调用新回滚；保持原路径处理后的业务状态及残留文本规则，只释放该次3D busy token |

同会话快照恢复也递增`sessionEpoch`；此字段实际表示“宿主数据代次”，不是持久存档ID。读档开始立即invalidate，在结果未定时不应用任何旧快照；成功/失败结束均在新的数据代次重新投影真实当前状态。

#### E. 生命周期时序的唯一预期

- mount初始化尚未完成连续收到r1/r2：只保留最新r2目标，不开两个renderer；r1完成返回superseded。
- 同epoch/revision重复apply：不重载、不重新抽NPC，不重复发ready或注册事件。
- 切档后目标仍为同一房间：允许复用安全模型缓存，但NPC/时间/菜单全部按新epoch重建，旧任务不能attach。
- destroy发生在parse/compile/多图加载中：立即禁副作用，允许无法取消的计算自然settle；每个成功获得的资源均登记拥有者，部分失败也释放。**纯候选dispose不能调用会解绑当前B场景的活动disposeRoom**；活动解绑与资源释放必须分开。
- 模块import用单个在途Promise去重；成功后模块可在本页面复用，实例不是单例死对象。加载失败清在途状态允许显式重试；同次会话固定构建版本，destroy不自动切换current指针。
- ready表示目标模型已编译并首次可显示；ApplyResult.applied表示目标状态应用完成；interactive还受宿主锁/可见性控制。收到ready不等于可以打开controls。
- 每个mount有独立`instanceId`，显式retry递增渲染`attemptId/routeGeneration`而不伪造业务revision。去重key含instanceId、epoch/revision、任务有效性；失败/取消不缓存为“已成功应用”。bridge保存最新有效快照，新实例无条件接收它。
- 404→资源修复→点击重试：同地点/epoch/revision，view.retry重新加载；若实例已destroy，bridge新mount再apply同快照。普通重复notify不触发失败无限自动重试，须显式retry或实际生命周期恢复。
- 隐藏时取消了任务→显示恢复：bridge重新校验宿主资格，向同/新实例应用最新快照，不能因revision相同而跳过。`pagehide`销毁后，BFCache的`pageshow`同样重建并应用，不读取旧控件/旧promise当ready。
- 信息卡仅需静帧时用setRenderEnabled(false)，不是setVisible(false)；因此不会切回2D或取消已完成场景。关闭一层卡不自动停用其余锁；最后解锁且宿主允许时恢复rAF。真正进入Gal/隐藏页面才走setVisible(false)/卸载计时。

#### F. 静态人物不能假装成动态图集

统一内部VisualDescriptor为`animated | static | list`三种：animated包含sheets、frameCount、delays、duration、bounds、height；static包含imageUrl、加载后的width/height、有效alpha bounds（缺失时整图）、height且只有一帧；list仅有gameNpcId/displayName/原因。static不得直接传给依赖sheets/delays的pro动画路径。

图片成功解码后再按实际宽高与alpha边界生成卡片比例；透明命中使用缩小的alpha mask并校验bounds，不能用固定假frame尺寸。CORS/getImageData失败、无有效像素、过大纹理或设备maxTextureSize不足均退同角色列表，不把透明矩形整块变成可点人物。3D静态与动态人物共享菜单协议，列表的屏幕锚点用自身按钮rect。

### 14.2 P0必须先建立的测试底座（不是留到P5）

默认用**Node内置node:test + puppeteer-core**。没有引入另一套前端框架的必要。待创建命令面固定如下，按首次可用阶段实现并写进README：**P0只要求test:unit/test:browser及2D基线，P1才要求import-assets/build/publish:assets/verify:web，P5补verify:staging/verify:apk**。不得用返回成功的空脚本假装命令已交付。

依赖解析固定为：`scene3d/package.json`声明`type:module`；runner/第三方依赖helper位于`scene3d/scripts/*.mjs`，从本包node_modules解析。根`tests/scene3d/**/*.mjs`仅import Node内置或显式相对路径helper，不直接裸import three/puppeteer-core；`npm --prefix`不会改变兄弟目录的Node解析规则，不往游戏根安装依赖补救。

待创建package scripts的真实入口约定为`test:unit = node scripts/run-unit.mjs`、`test:browser = node scripts/run-browser.mjs`。run-unit用Node测试机制运行显式发现的.mjs纯测试，run-browser负责server/BrowserContext/fixture/报告；helpers由`scene3d/scripts/test-support.mjs`导出受控功能。P0只能执行宿主完成条件和已冻结协议纯测试，不能等尚不存在的renderer.applied。

```powershell
# cwd=<完整隔离游戏副本根>；scene3d/package.json和lock创建并审查后
npm.cmd --prefix scene3d ci
npm.cmd --prefix scene3d run test:unit
npm.cmd --prefix scene3d run test:browser -- --phase=P0 --reportDir='<本run报告绝对路径>'
# 后续按P1...P6选择；--phase=all代表P0–P6全部必测，缺实现不能返回成功
# P1以后构建命令需显式输入输出，见14.6 CLI契约；本段不执行未来脚本
```

- P0首次创建package/lock需要显式记录依赖安装（可能下载/执行依赖脚本）；依赖版本冻结后用ci。ci会重建该局部包的node_modules，不能在pro或原apk目录盲跑。
- `test:unit`覆盖纯协议/ID映射、版本校验、seed、失效规则与资源清理模拟；`test:browser`启动真实游戏HTML，不以另造简化页面冒充端到端测试。
- test:browser拥有一个loopback-only静态测试server（随机可用端口0，启动后输出实际URL），根目录只指向本次副本并拒绝路径穿越。runner记录server/浏览器PID，在finally仅关闭本run创建的进程，不杀用户浏览器/服务器。
- 复用既有测试URL必须显式传入并核对其根与版本；不能探测一个恰好可访问的端口后默认为本项目。最终生产测试另用构建产物，不用Vite dev代替。
- 每个case新BrowserContext/profile，不连接用户真实浏览器；每run使用随机生成的测试标识，清localStorage/IndexedDB/CacheStorage/SW只在本run上下文和测试origin内执行。**不同URL子路径不是隔离origin。**
- rAF和performance使用真实时钟；只固定业务Date/显式业务随机入口。为了保留原行为，可在业务script前注入带计数的Math.random伪随机发生器；3D实现必须另用私有seed，比较同业务操作轨迹的RNG计数。
- 外部网络默认拒绝：仅允许测试server资产、被匹配的fixture API和必要data/blob。主LLM、摘要runner、嵌入/召回、重试端点都必须拦截，未匹配外发直接FAIL而不是悄悄走真实服务。
- 浏览器新document加载前使用evaluateOnNewDocument注入测试标志/假配置及fixture装载器；测试资产只在测试server路径提供，不打包进assets发布目录。
- 状态观测通过**测试专用classic探针**读取顶层let，不用window.GameMode；探针由runner在页面脚本执行后注入、只返回脱敏普通对象。不能通过调用sync函数读取快照；生产不留可任意改档的全局debug API。
- 每个阶段设置确定的完成条件：宿主初始化终点、提交/恢复事务终点、bridge最新revision以及renderer.applied。可增加只读test hook观察既有函数结束；禁止用固定sleep认定成功。测试本身有上限timeout，超时FAIL并收集状态。
- 流式fixture必须按实际api-service期待的SSE或JSON格式提供，含完成标记、分片、中断和HTTP错误；不能直接写最终gameData跳过parser/pipeline来声称LLM链通过。纯bridge单测可以注入snapshot，但与完整业务E2E分开标记。
- **真实流式运输**由本run的loopback测试server提供mock API端点：按fixture的status/headers/steps逐步HTTP write，等待runner确认应用已经消费指定段落后才放行下一步，支持正常end、保持连接、断连与abort记录。Puppeteer request.respond一次性返回完整SSE字符串只能测解析，不能作为“流式途中取消”的证据。配置请求指向模拟端点，其他外发仍拒绝；不要断言TCP物理分包边界。
- 响应fixture应有`status`、`headers`、`steps`（body片段、等待的应用检查点/runner放行token）、`terminal=end|disconnect|await-abort`及预期请求次数/提交次数。控制端点带本run随机token，仅loopback接受，测试完成后关闭连接和server。
- 维护固定测试registry：每个ID标firstPhase、必测/人工、fixture与完成条件。`--phase=Pn`运行本阶段必测+声明的既有smoke；必测缺实现、FAIL/BLOCKED/NOT RUN均非零。纯列出计划使用`--list`，不生成PASS；`--phase=all`必须覆盖全部必测而非“已有脚本”。人工项只有绑定同版本证据/具名评审才算完成，不由runner自动判PASS。

P0新增交付：runner/static-server、独立浏览器隔离、固定Date/RNG计数、默认外发拒绝、classic只读探针、diff比较器和一个真实2D固定响应smoke。没有这些，P0-T03没有可复现依据，不能通过。

每份测试夹具由manifest描述，真实存档payload按原游戏导出格式保存，不能为了方便改成测试私有格式后绕过导入流程。

```json
{
  "id": "cultivation-library-v1",
  "format": "game-json-export",
  "sourceRevision": "由P0填写",
  "payloadFile": "saves/library.json",
  "payloadSha256": "构建夹具时填写真实摘要",
```

实际夹具必须补齐当前用例所需NPC/数值/配置预期及操作步骤。`entry`分别支持真实已实现的开局、槽位、JSON、ST导入；ST格式必须有对应ST导出样本，不把普通游戏JSON喂给ST导入后硬改状态。全局提示词/API设置不在普通存档内，使用独立假配置夹具，读档后再断言继承规则。

Android测试不拿用户日用安装灌fixture。使用专用设备/Android测试用户环境并确认serial/applicationId；全新安装离线测试与保留数据升级测试是不同lane。不得为冷缓存测量对用户应用执行pm clear/uninstall。HAR/header、截图、崩溃日志可能含正文和key，脱敏后再归档；私钥只由拥有者管理。

### 14.4 版本化3D资源与不可变发布

目录采用`assets/sect3d/<buildId>/`，buildId为独立发布标识（例如受控时间戳+源摘要短码），**不由包含自身路径的输出manifest循环计算**。同buildId内容不可覆盖。所有文件先生成到临时build目录，完整校验后发布，最后切换current.json。

```json
// current.json结构示意；实际文件为合法JSON，不含注释
{
  "schemaVersion": 1,
  "buildId": "example-build-id",
  "bridgeProtocol": { "min": 1, "max": 1 },
  "manifest": "example-build-id/manifest.json",
  "manifestSha256": "发布时填真实摘要"
}
```

```json
// <buildId>/manifest.json结构示意；所有entry/css都必须在files集合内
{
  "schemaVersion": 1,
  "buildId": "example-build-id",
  "bridgeProtocol": { "min": 1, "max": 1 },
  "entry": "entry.mjs",
  "css": ["scene3d.css"],
  "files": {
    "entry.mjs": { "bytes": 0, "sha256": "此处仅示意，不是有效产物" },
    "scene3d.css": { "bytes": 0, "sha256": "实际构建必须填真实值" }
  }
}
```

实现要求：

1. 游戏静态根按当前游戏文档URL解析`./assets/sect3d/current.json`，同时适用于站点子路径index.html和APK game.html；不加全局`<base>`。assetBaseUrl为已验证版本目录的绝对URL且带尾斜杠。
2. 一次页面会话只取得并冻结一次pointer/manifest，entry、CSS、动态chunks、GLB、NPC和Draco全部来自同版本。关闭再开启不自动追新；用户整页刷新才选新版本。
3. pointer无缓存或要求重新验证；版本目录immutable。加载CSS须等load后再mount；CSS/动态import的晚到结果也检查epoch/实例状态。样式按版本引用计数，彻底卸载最后实例时可移除，无全局副作用。
4. `assetBase`用于手工fetch；Vite本身的import chunk、CSS url、worker资源必须相对输出路径可用。明确导出mount的ESM library入口，不发布原pro预览HTML；生成非隐藏manifest.json，不能依赖Android会忽略的`.vite/manifest.json`。
5. release文件路径使用相对POSIX路径；允许中文资源路径但拒绝绝对路径、协议URL、`..`/`.`段、反斜杠、编码穿越、大小写碰撞及symlink越界。URL解析后仍须同origin且在本版本根内；静态原NPC立绘是额外受控宿主资源白名单，不经外部URL注入。
6. pointer/manifest protocol与buildId必须匹配；旧bridge遇到不兼容pointer保持2D并提示刷新，不盲目import。所有声明资源必须存在，主模型缺失也必须构建失败，不能只warn。
7. manifest自身hash放pointer/外部交付记录，不自包含。构建/发布校验逐文件SHA256并拒绝版本目录中清单外文件（manifest本身除外）；摘要用于一致性，不是发布者签名。运行时若仅检查manifest摘要而未逐模型hash，就不能宣称所有fetch均实时验完整性。
8. 网页先上传完整新版本再最后更新pointer；保留旧版本供仍运行的旧会话继续加载，不无提示删旧GLB。APK只含当前版，pointer不能指远程开发地址，失败直接2D，不联网追latest。
9. 偏好存储失败/JSON损坏时默认关闭3D、low配置并可在当前会话手动启用；不因此清用户其他localStorage。file协议不请求3D资源，解释仅HTTP(S)/WebView支持3D。

### 14.5 Web→APK的三层清单与复制规则

**不能要求网页源目录与APK public目录完全相等。** 当前apk/build.js有入口重命名，Capacitor同步还生成文件。要证明的是可解释的映射和同一3D资产版本，而不是错误的一对一全站hash比较。

| 清单 | 来源与约束 | 校验对象 |
| --- | --- | --- |
| 输入基线 | 游戏/pro源码快照、dirty内容、锁文件/构建配置hash、工具版本 | 证明产物由哪个源码/依赖版本生成，不只验证已有bundle |
| 3D release清单 | 构建输出，不含预览工具/历史/Blend | version目录精确集合、entry/CSS/chunks/GLB/NPC/WASM hash |
| Web/APK暂存映射清单 | 审读后的游戏复制规则和入口变换 | Web的index→APK game、start-screen-noST→APK index及intent改写；原资源保持hash |
| Capacitor同步后清单 | **由上层预期+受控工具生成项推导，先比较再记录** | Android assets/public精确集合；公共文件与APK ZIP逐字节一致 |
| 外部交付记录 | 上述清单hash、APKhash、版本/签名/测试lane | 不被包含在自己的hash里，绑定最终受测产物 |

正式复制规则：

- 原普通`assets`递归复制必须**排除`assets/sect3d`**；之后读取并冻结一次current，按manifest单独复制pointer+当前buildId。不能先复制所有版本再期待Capacitor删除，也不能为缩包删源目录旧版本。
- 其余原目录/HTML白名单保持；缺必需入口、JS、当前3D资源时立即非零退出，不能像原脚本部分路径那样warn后继续。
- 暂存目录只能是明确派生输出；原`apk/build.js`的DEST由`__dirname`固定到apk/www，**改cwd不会改变输出**。未改造outDir前必须在完整游戏隔离副本执行，不得声称指定任意cwd就安全。
- Web包保留原入口；APK仍由index开局→game.html。已有重复开局页跳转按实际访问路径测试，不把原ST外链一并重写。
- 当前Capacitor 8即使无Cordova插件，也可能生成`public/cordova.js`、`public/cordova_plugins.js`空文件；应按锁定CLI源码确认允许的精确文件和内容，加入预期集合，不泛化允许任意`cordova*`。
- `assets/capacitor.config.json`及`assets/capacitor.plugins.json`在public外，单独验证appId/webDir/https-localhost配置、无远程server.url、Filesystem/Share实际插件清单与原生工程依赖。配置会重序列化，用语义比较再记录实际hash，不能要求与源JSON空白一致。
- 禁止“扫同步后目录生成manifest，然后拿它校验自身”——这会把残留旧bundle也合法化。先依据输入映射和工具生成白名单拒绝未知增删改，再产同步后清单，最后验APK ZIP。
- Android运行时会向HTML注入Capacitor bridge/plugin脚本。hash对象是ZIP内文件，不是WebView outerHTML/运行时响应。3D局部包不带Capacitor 6/8、不重复注入桥；首版不新增可能阻断宿主内联脚本/原生注入的严格CSP。

### 14.6 后续实施时的构建/设备操作顺序

每步检查退出码，失败立即停止后续；失败后旧APK/旧manifest不能冒充新成功。Windows优先用npm.cmd和明确本地CLI，避免npx找不到时隐式下载安装。

**待创建CLI的输入/输出契约**（P1先实现资产导入/构建/发布，P5补完整游戏暂存校验）：

- 一个run先由实施者确定`runId/buildId`，在`<副本根>/.scene3d-work/<runId>/run.json`记录副本根、sourceManifest hash、锁文件hash、buildId与所有输出绝对路径。`.scene3d-work`是测试/构建工作目录，不部署到Web/APK；不得通过mtime猜“最新目录”。不同run不得共用可写输出目录。
- 所有脚本首参为`--runRecord=<run.json>`，其它路径在此记录内冻结并校验，只允许显式批准的副本/源根；若传入命令参数与记录冲突则失败，不默默覆盖。脚本记录开始/结束状态，旧成功记录不替代本次失败。

| package script / 待创建入口 | 显式输入 | 固定输出/规则 |
| --- | --- | --- |
| `import-assets` / `scripts/import-assets.mjs` | runRecord内`sourceRoot=<pro基线副本>`、`sourceManifest=<P0白名单>`、`resourcesRoot=<游戏副本>/scene3d/resources` | 只复制已列模型/图集/decoder并校验hash；不会递归复制pro；输入资源清单写入run目录 |
| `build` / `scripts/build.mjs` | runRecord内buildId、resources清单、源码/lock/config hash | 调用局部Vite输出到`.scene3d-work/<runId>/release`，生成非隐藏manifest；记录releaseDir/hash，不能写其他run |
| `publish:assets` / `scripts/publish-assets.mjs` | 同run已验证releaseDir、`publishRoot=<副本>/assets/sect3d` | 完整写新buildId目录并校验，最后原子写pointer；buildId已存在而内容不同即失败 |
| `verify:web` / `scripts/verify-web.mjs` | 同run releaseDir或已发布buildId目录、预期manifest | 只读检查精确文件集合及hash，报告写run；不会修补缺资源 |
| `verify:staging` / `scripts/verify-staging.mjs` | 同run`wwwExpectedManifest`（由改造的apk/build.js在复制时生成）、原生工具生成项契约、androidRoot | 先比对同步后目录，成功才写`.scene3d-work/<runId>/android-staging-manifest.json`；不对未知文件自我授权 |
| `verify:apk` / `scripts/verify-apk.mjs` | 同run的新APK路径、已通过的android-staging-manifest及预期原生配置 | ZIP精确集合/hash/原生语义报告，记录APK hash；不构建、不安装 |

导入的resources必须有生成文件清单，原目录存在手工文件或不同baseline时先停止；不使用对任意路径的rm -rf。sourceManifest分明“输入库存”和“可发布运行时文件”，参考图/Blend/截图可登记输入但不进运行资源。若未开放厢房模型仍被保留，manifest明确该文件非业务可达，不让构建器硬编码只有可达的11文件。

示例命令序列中，下文所有局部npm脚本都追加`-- --runRecord='<本run绝对路径>'`。P1临时APK smoke也登记同run，不能绕过资源来源；P5正式改造`apk/build.js`时增加`--runRecord`参数，产wwwExpectedManifest并只清理本副本www。未改造前原`node build.js`仍固定输出，不可假装支持这个参数。

| --- | --- | --- |
| 依赖 | `<副本>\scene3d`：`npm.cmd ci` | 锁文件→局部node_modules；可能下载/重建目录 |

### 15.2 一轮开发/续作的标准操作

1. 读本入口、当前阶段验收记录和`开发文档/3D整合/实施日志.md`（待创建）；查cwd/Git状态。没日志时从P0开始，不凭前次聊天推定已完成。
2. 校验当前源码/模型与输入manifest；变化只重查相关源码与测试，不把旧行号当事实。若其他人正在改同文件，先协调边界，不覆盖其工作。
3. 每个改动先写或更新对应测试预期，再做单一目标最小patch；不混全局重构与3D接入。列出本轮允许改文件、要执行命令及副作用。
4. 执行当前阶段最小测试，再回归已完成阶段smoke；每次失败记录真实命令/环境/输入，定位原因再修复，不能反复运行到偶然绿。
5. 写回实施日志：已完成任务/改文件、协议/资产版本、实际命令和结果、证据路径、剩余项、阻断、下一步。长命令/服务器记录job/PID，只清理自己启动且不再需要的进程。
6. 阶段审查核对产物与报告同版本；测试PASS与“未执行”明确区分；完成阶段后再继续。不要把本手册中的未来样例命令输出复制为结果。

建议实施日志记录格式：阶段/子任务、输入版本、输出文件、测试ID与状态、缺陷编号、待决问题、下一条可执行动作。文档较长时只读当前相关章节，但协议/默认决策一旦变更必须同步其他受影响章节，避免多处出现不同接口。
