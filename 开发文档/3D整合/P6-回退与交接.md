## 1. 三种回退不得混称

| 路径 | 实际动作 | 不代表什么 |
| --- | --- | --- |
| 游戏内关闭 3D | 通过宿主既有 3D 开关停绘、禁输入、卸载组件，恢复原 2D 背景/人物/操作 | 不回滚地点、NPC、行动点、正文、存档或业务版本；不能以视觉回退掩盖未完成的主功能 |
| 本文 Web 指针激活 | 将 `assets/sect3d/current.json` 指向一套已存在、已验证的完整不可变 3D 资源版本 | 不复制旧 JS 覆盖新模型；不改变宿主 HTML/classic 业务脚本；不是浏览器最终显示验收 |
| APK 应急版本 | 使用兼容证书、符合版本号规则的新应急包，优先默认关闭 3D | 不是 `adb install -d`、卸载重装、清数据，也不是直接安装旧低 versionCode 包 |

Web 指针只改变 **3D 资源版本**。如果目标 3D 协议或宿主业务脚本不兼容，需维护者另外确认完整宿主版本组合；不得把协议 1 的存在等同于所有业务行为兼容。已打开会话按既有组件协议锁定其资源版本，不强迫活动剧情页面热切换；重新加载前先按本说明备份。

## 2. 已实现 CLI 契约及独立操作 run

脚本入口：`scene3d/scripts/activate-release.mjs`，仅允许三个显式参数：

```text
node scene3d/scripts/activate-release.mjs \
  --runRecord=<本次独立激活操作的绝对run.json> \
  --targetRunRecord=<目标历史构建run.json的绝对路径> \
  --expectedCurrentBuildId=<操作前人工确认的当前buildId>
```

Windows PowerShell 实际使用一行命令，或反引号换行；上面的反斜杠只是参数列表展示，不是可直接执行的 PowerShell 语法。

约束：

- 首参必须为 `--runRecord=...`，路径必须绝对且规范化；不接受 `--force`、未知参数、重复参数或目录穿越。
- 本次操作使用**全新的** `.scene3d-work/<activationRunId>/run.json`，不能拿目标历史 build run 或既有发布 run 当操作记录覆盖。操作记录 `buildId` 填本次要激活的目标 buildId；其 `releaseDir` 只是 run 配置字段，本脚本不构建也不创建该目录。
- 使用现有 `run-record.mjs` 创建新 run，显式填写项目根、历史源清单等冻结路径；新操作 run 必须通过当前配置与锁文件校验。不要手工改历史 run 的 frozen 字段迎合校验。
- 目标历史 run 必须属于同一 `projectRoot` 和 `publishRoot`，必须有成功的 `build` 与 `publish:assets` 记录；目标归档 `release` 和目标发布目录必须已经存在。
- 历史目标验证其冻结配置、归档 manifest 及构建/发布记录，不要求它的旧依赖锁 SHA 与当前 live 锁文件相同。回退不读取/恢复旧 `node_modules`、不改锁文件、不重新构建；真正信任对象是目标归档和已发布文件的逐字节证据。
- 每一次回退、再次激活、失败重试均分配新的 operation run。旧失败不冒充成功，旧证据不被同路径覆盖。

### 操作示例（全部替换为现场已核对值）

```powershell
# cwd 为经批准的游戏副本根；先准备新 operation run，不借用 build run。
node scene3d/scripts/run-record.mjs --runRecord='E:\部署副本\.scene3d-work\rollback-001\run.json' --runId=rollback-001 --buildId=known-good-build --projectRoot='E:\部署副本' --sourceRoot='E:\冻结源副本' --sourceManifest='E:\冻结源清单.json' --resourceRoot='E:\部署副本\.scene3d-work\rollback-001\resources' --releaseDir='E:\部署副本\.scene3d-work\rollback-001\release' --publishRoot='E:\部署副本\assets\sect3d'

# 核对 expectedCurrentBuildId 后才执行；不能从“上次应该是...”推断当前值。
node scene3d/scripts/activate-release.mjs --runRecord='E:\部署副本\.scene3d-work\rollback-001\run.json' --targetRunRecord='E:\部署副本\.scene3d-work\known-good-run\run.json' --expectedCurrentBuildId=current-build
```

再次激活更新版本时流程相同：新建另一个 operation run，目标换成已存在的更新 build run，`expectedCurrentBuildId` 必须填回退后实际当前版本。不能重用前次的 expected 值，也不能复用旧 operation run 证据目录。

## 3. 验证、原子切换与竞态边界

脚本已按以下顺序实现：

1. 验证 CLI、新操作 run、目标路径归属；在本 run 建立独立激活证据目录。
2. 使用与 `publish-assets.mjs` 相同的 `<publishRoot>/.publish.lock` 排斥其他协作发布/激活。锁已存在则失败；不得抢占或自动删除疑似陈旧锁。
3. 读取 `current.json` 的原始字节及解析结果；核对 schema、完整 manifest 路径/hash、支持协议 1 及显式 `expectedCurrentBuildId`。
4. 保存之前 pointer 的原始 JSON 字节及 SHA-256/字节数摘要。
5. 目标历史 run 的成功 build/publish 必须指向同一目标 release/manifest hash。分别验证目标归档 release 与 `assets/sect3d/<buildId>/` 的 manifest 原始 hash、完整文件集合、每个文件的 bytes/SHA-256；中文资源路径按原字符保留。拒绝缺文件、额外文件、同长篡改、manifest 篡改、路径大小写/Unicode 冲突、symlink/junction。
6. manifest 的 `bridgeProtocol` 必须明确包含协议 1；只激活完整目录，不从另一代版本补文件。
7. 在提交前再次核对目标证据及 pointer 的原始字节，不能只比较 buildId。先持久保存 `prepared` 证据，再用**同目录临时文件 + rename**原子替换唯一可变 pointer。
8. 校验替换后的 pointer 并保存 `committed` 证据、本次 run 成功状态。目标本已处于激活且字节一致时记录无变更验证，不复制资源。

### 不夸大的保证

- 同目录 rename 保证读者看到旧或新完整 JSON，不看到半份 JSON。
- `.publish.lock` 与提交前原始字节复核防止协作发布进程和过期操作命令误覆盖。
- 这不是跨任意进程的数据库事务。若有人绕过锁直接写 pointer/不可变版本目录，无法承诺消除所有 OS 级 TOCTOU；运维必须统一通过受控工具发布，并禁止并行人工覆盖。
- 提交前失败：本脚本不改变 pointer，独立证据/本 run 标记失败。若是另一个绕过锁的写入者改了 pointer，本脚本拒绝覆盖其结果，不能把该外部变化伪称为本脚本提交。
- 提交后写证据失败或进程中断：不能把它解释为“绝未切换”。现场核对实际 pointer/hash 与 `prepared` 中的目标。脚本不得为了补救日志失败而自动盲目覆盖后来已更新的 pointer。
- 锁在异常退出后遗留时，先确认进程、目标文件、证据状态，再由维护者显式处理；不内置自动扫锁或删除其他版本的清理程序。

## 4. 本次操作证据

固定目录：`.scene3d-work/<activationRunId>/activation/`。该目录必须不存在，由本次操作独占创建；已有证据或已有 `activate-release` step 时拒绝复用。参数/路径预检失败发生在进入操作之前时，不生成一份伪运行证据，以 CLI 非零退出为准。

| 文件 | 内容 |
| --- | --- |
| `request.json` | 本次 run、目标历史 run、expected 当前版本、开始时间及操作范围 |
| `before-pointer.json` | 之前 pointer 的原始字节副本，不是重新格式化后冒充原字节 |
| `next-pointer.json` | 本次准备提交的完整目标 pointer |
| `target-manifest.json` | 经校验的目标 manifest 原始字节，用于复核资源集合和各文件摘要；不复制资源载荷 |
| `transaction.json` | `preparing/prepared/committed/failed`、`pointerCommitted`、before/target/after 的路径与 bytes/SHA 摘要、错误及限制 |
| 本 run 的 `run.json` | `activate-release` 本次 step 状态及证据文件/hash |

证据只含资源/运行路径与发布元数据，不含 API key、提示词、剧情正文、真实存档内容。真实存档备份另存用户授权的受保护目录，不能混进发布资源或 Git。

## 5. 自动化与“旧数据不变”的正确解释

限定测试入口：

```powershell
# cwd：E:\JJBurst\git（或完整隔离副本根）。
node --test tests/scene3d/release-unit.mjs
```

测试只在新建的 `os.tmpdir()` 独立 fixture 根下操作，不触碰工作区实际 `assets/sect3d/current.json`、真实存档、原 APK 或用户浏览器配置。

覆盖：

- 旧版本回退、再次激活、已激活目标无变更验证；中文 buildId/资源路径。
- 缺目标发布目录、缺文件、额外文件、同长度内容篡改、manifest/归档篡改、未知 run/失败 provenance、冻结配置变动。
- 不含协议 1 的拒绝、包含协议 1 的显式兼容范围。
- expected 当前版本不符、并发激活调用争用 `.publish.lock`、已有锁不得删除。
- 在 `prepared` 后注入同 buildId、不同原始字节的越锁写入，提交前检查拒绝覆盖；提交后注入另一版本的越锁写入，报告 `pointerCommitted=true` 的失败，绝不盲目回滚。
- 通过 Node 子进程调用实际 CLI，验证成功退出 0、过期 expected 值退出非零。测试中故意打印的 expected/current 不符错误属于负测预期，不是套件失败。
- 历史依赖锁与当前 live 锁不同时，基于归档资源回退且 live 依赖不变。
- 旧 build run 只读、独立证据禁止覆盖、symlink/junction 输出拒绝。
- dummy 存档/API配置/原APK哨兵文件回退前后 bytes/SHA 不变，其他发布版本及旧记录也不变。

**“旧数据不变”仅证明本脚本没有读写游戏数据/存储/APK的路径，以及隔离文件哨兵保持不变。** 它不证明旧应用能解析新存档，不替代真实浏览器存读档、不替代手机升级保留数据测试，不将 dummy 导出文件称为用户真实导出档。

## 6. APK 身份、签名和版本号

本项目给定原应用身份基线：

- `applicationId/appId`：`com.jihaitang.jxz`
- 已知原 `versionCode`：`4`
- 已知原 `versionName`：`1.3`

以上是给定基线，不代替读取现场真实旧 APK 与设备已安装包。若现场已安装 code 更高，应以现场为准。

正式覆盖前必须核对：

1. 同一 applicationId，兼容签名证书/受平台支持的签名 lineage；仅名称相同或同属 debug 不等于兼容。
2. `versionCode` 不得下降。正式新发行/本计划覆盖升级测试优先要求严格更高；同版本覆盖仅在明确允许的专用测试条件下验证，不能作为正式回滚策略。
3. versionName 是显示版本，不是替代 versionCode 的升级判定。
4. 证书不匹配、无真实旧包、版本规则不满足、无测试设备时，真实覆盖升级 lane 标 **BLOCKED/NOT RUN**；不能卸载/清数据后安装来补一个假 PASS。
5. 紧急回退优先发布 **更高 versionCode、兼容签名、默认关闭 3D** 的应急包。不要盲装旧低 code APK，不要求用户打开降级安装或清除全部游戏数据。

复制 APK、校验 ZIP 网页文件、桌面 current 指针切换、全新 debug 安装，都不是“真实兼容签名升级成功”的证据。

## 7. 真实存档保全与数据兼容

发布、覆盖升级、应用版本回退之前必须：

- 用游戏真实导出流程保留多代备份，至少包含升级前、关键游玩后、拟回退前的导出；不得只有一个会被覆盖的文件。
- 每代记录游戏/资源版本、导出时间、SHA-256、字节数及脱敏备注；用户真实内容受保护存放，不入代码仓库/公开报告。
- 在获准的独立测试会话/测试设备中**实际导入确认**，核对地点、模式、NPC、行动/数值、历史和存读档往返；只确认“JSON能打开”不算备份可用。
- 保留原文件，不用导入工具修复时覆盖唯一备份；若旧版本无法读取新版本档，禁止声称资源回退自动解决了数据兼容。
- Web 指针脚本不读取、更不迁移 `gameData`、localStorage、IndexedDB 或 APK 私有数据；数据兼容由单独经批准的游戏测试负责。
